# Shepard, PT, Cartography, And Worlds Roadmap

Status: Discussion record / planning note
Owner: Product / Frontend / Backend
Created: 2026-05-08

## Purpose

This document preserves the main conclusions from the Shepard_4 refactor discussion and the later product discussion around PT, Cartography, user-created worlds, and the Worlds surface.

The goal is not to prescribe one immediate implementation. It is to keep the conceptual decisions available so future development can continue from the same vocabulary.

## Core Lineage

Shepard_4 began as a musical generator where a user explored a bounded space of possible music. The important idea was not the old implementation. The important idea was:

```text
coordinates in a possibility space
  -> select / rotate / sample musical material
  -> produce a concrete progression
```

PT and DCN already generalize much of that machinery:

```text
Shepard start / pitch coordinate   -> PT RI start_point
Shepard rotation                   -> PT RI transformation_shift
Shepard skip / further selection   -> connector nesting and value selection
Shepard circular transformation    -> cyclic transformation lists in connector dimensions
Shepard generated progression      -> connector execute output streams
```

The remaining Shepard-inspired idea worth preserving is the act of **mapping a space of possible structures or values before the final musical object is manually authored**.

## Conceptual Stack

The system should separate these layers:

```text
PT / DCN
  world-agnostic protocol for connectors, transformations, conditions, formats, and execution

Hypermusic Studio
  authoring environment for connector graphs, RI values, worlds, and execution previews

Cartography
  optional assistant-driven tool for exploring possible connector structures from a toolbox

Worlds
  published visualizers / generative environments that consume connector states

Worlds
  public surface for browsing worlds and rendering compatible connector/RI states
```

Cartography is optional. It is one available tool, not a required step in the world flow.

## Circular Musical Material

The generalized Shepard model should treat every musical parameter as a sampled circular parameter space:

```text
pitch
onset time
duration
velocity / dynamic
staff
voice
articulation
register
timbre
```

Each parameter can be generated by similar ideas:

```text
divide space
choose offset
choose skip / stride
choose phase / rotation
sample values
bind sampled values into score/world positions
```

For Music Score output, sampled streams are bound through the existing positional schema:

```text
NOTE_TABLE
├─ D1 onset_tick
├─ D2 duration_tick
├─ D3 pitch
├─ D5 part
├─ D6 staff
├─ D7 voice
└─ D8 dynamic_code
```

Semantic meaning should remain positional. Connector names can help readability, but they should not define score meaning.

## Cartography

Cartography is not a recommendation engine. It should not decide that one element is musically better than another.

Cartography should:

- work only with the user's current toolbox;
- generate a navigable possibility space of connector structures;
- expose coordinates as precomputed assistant build intents;
- explain structural consequences;
- validate whether a coordinate can be spawned into Studio;
- avoid suggesting missing elements in the initial version.

The useful framing is:

```text
LLM assistant creates a latent map of possible connector structures
  -> each coordinate is a compressed build intent
  -> deterministic validation filters the map
  -> user clicks coordinates to spawn connector scaffolds
```

Cartography should reuse the existing Studio assistant's knowledge of Music Score connector construction, but present the result spatially rather than as a chat transcript.

## Worlds

The user-facing concept should be **World**, not plugin.

A world is:

```text
a published visualizer / generative environment for DCN connector states
```

More specifically:

```text
World runtime
  self-contained web project stored on IPFS and loaded in a sandboxed iframe

World render input
  compatible connector + runtime RI values
```

This is analogous to fxhash generative artworks at the level of loading a self-contained visualizer, but the render input is different and Hypermusic should not copy the collected-iteration storage model:

```text
fxhash:
  generator code + deterministic random hash -> collected iteration

hypermusic:
  world visualizer + connector + runtime RI values -> world render
```

The world renders:

```text
1. a given compatible connector
2. runtime RI values supplied to that connector
```

Hypermusic should not store user-selected RI iterations. RIs are already the runtime space of the DCN protocol. If RIs are open, the user inserts values at runtime and the visualizer reads the resulting connector output. If a result must be fixed permanently, the connector/configuration itself should be saved with static RI values.

The world creator creates a visual environment for compatible connector/RIs states. The protocol object remains the connector and its RI behavior, not a separate stored iteration.

The same world runtime should be usable in both Worlds and Studio:

```text
Worlds
  browse worlds, choose compatible connector/RI values, and render them in a sandboxed world iframe

Studio
  connect a compatible connector to a world inlet
  run the connector
  send the result into the same sandboxed world iframe
```

For the MusicXML world, Studio should keep the current inlet-based workflow that previously belonged to the Music Score plugin. The difference is that the renderer becomes an isolated world runtime: the trusted Studio host converts connector output into MusicXML, then passes the MusicXML payload into the sandboxed iframe.

Current reference connector for testing this flow:

```text
test_score_root_0_version2_6052026
```

## Protocol Boundary

Worlds should not be part of `dcn-server`.

PT and `dcn-server` should stay world-agnostic:

```text
connectors
transformations
conditions
formats
execute
```

The vocabulary of worlds should begin at the Hypermusic social/application layer:

```text
hypermusic-backend
hypermusic-frontend
optional separate world registry contract
IPFS storage
```

This preserves DCN as a general protocol for heterogeneous connector composition while allowing Hypermusic to host and index worlds socially.

## Repo Impact

Expected first-class changes:

```text
hypermusic-frontend
hypermusic-backend
```

Potential later additions:

```text
separate world registry contract
dcn-sdk/spec only if world runtime APIs become public SDK contracts
dcn-mcp only if MCP should inspect or create worlds
```

Not expected for the world vocabulary:

```text
dcn-server
PT core protocol
```

PT/DCN may still be used by worlds, but should not become world-specific.

## Practical Roadmap

1. Preserve and refine Shepard_4 as a reference for circular musical material.
2. Prototype circular material generation using PT-compatible streams and the MusicXML Score World.
3. Add the optional Studio Cartographer tab for toolbox-bounded connector-space exploration.
4. Define `WorldManifest` and `WorldRuntimeInput` schemas.
5. Build a local `/worlds` prototype with sandboxed iframe worlds.
6. Add Studio "Open in World" for connector/RIs runtime values.
7. Add backend world upload, validation, and IPFS pinning APIs.
8. Add on-chain world metadata only after the off-chain/IPFS flow is stable.
