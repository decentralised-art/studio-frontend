Tutorial

Introduction

What is decentralised.art?

decentralised.art lets humans and AI agents create reusable onchain procedures for Worlds. Contributors publish, combine, and run executable modules through the Studio and a shared Application Programming Interface (API), but the purpose is larger than API access: decentralised.art provides a procedural substrate that Worlds can interpret.

The protocol used in decentralised.art is called Performative Transactions (PT). It is meant for building:

collective performative intelligence

scalable expert systems where many participants contribute interoperable operations and gain from the intelligence of the network.

autonomous worlds and artworks

blockchain-based behaviours, operations, and conditions for autonomous objects, decentralised games, and NPC-player interactions.

autonomous economic systems

smart contract-based behaviours, incentives, and programmable conditions in self-governing economic networks. AI marketplaces, hybrid organisations, and resilient agent swarms.

intelligent delegation

execution and provenance layer for programmable delegation across humans and AI agents. Define roles, constraints, conditions, and verifiable histories of execution.

Worlds interpret procedures.

decentralised.art is not itself a single World. A World is an artwork, interface, simulation, game, or application that decides how connector outputs become meaningful. decentralised.art stores and exposes reusable procedures; Worlds interpret them.

In the current app, MusicXML Score World interprets compatible pitch, onset, duration, and expression streams as notation material. MIDI World interprets compatible streams as MIDI clips. Tone World interprets compatible audio and visual scalar streams as sound and generative image behaviour.

The same connector can become useful in more than one World when its output format matches what those Worlds understand. That is the practical path from reusable procedures to decentralised collective intelligence.

When do I want to use decentralised.art?

You use decentralised.art when you want behaviours to outlive apps, teams, and servers. When you care that an operation keeps working tomorrow, under explicit conditions, with no third party deciding whether it still runs.

  1. Persistence matters

    You want the operation to remain available as a stable reference (an address), not a link to a repo or a server that can disappear.

  2. Autonomy matters

    You want execution to depend on the operation's own logic and conditions, not on platform admins, service uptime, or API policy changes.

  3. Conditioning matters

    You need behaviours that trigger or constrain actions based on time, state, permissions, thresholds, identity, payments, governance signals, or external event feeds.

  4. Composability matters

    You expect many small mechanisms to be chained through dependencies, forks, and reuse into larger constellations.

  5. Multi-author contribution matters (humans + agents)

    You want many contributors to add interoperable modules, and agents to assemble them through an API.

Performative Transactions (PT)

PT is the protocol used in decentralised.art. In PT, connectors decide how flowing values are selected, transformed, gated by conditions, and combined. These flowing values are called particles.

At runtime, PT starts from one root connector, checks its condition, computes transformed streams on each dimension, and then either passes those streams to child connectors or emits them as output particle streams.

Particles

In PT, particles are the samples, values, and stream elements that flow through connectors. They become meaningful once mapped into a World, plugin, tool, or workflow.

Particles can represent pitches, durations, and velocities in music, but also colour channels, visual parameters, sample indexes, or other scalar value spaces defined by a World. decentralised.art rearranges them through connectors contributed by humans and AI agents building on each other's work.

Users build connector graphs, and those graphs determine how particles are received, transformed, and emitted across execution paths.

Connectors

Connectors are the runnable units of PT. A connector contains dimensions, transformations, optional child connectors, optional bindings, and a condition gate.

This is where users define the structure of execution: which child connectors appear on which dimensions, which transformations run, how child slots are wired through bindings, and which condition controls activation.

A connector:

  • receives particles on its dimensions,
  • applies transformations on those dimensions,
  • can connect to child connectors and wire them through bindings,
  • checks its condition,
  • emits output particles.

Connectors compose into larger graphs: one connector's output particles become another connector's input particles.

Example 1

In music composition

a connector over musical pitch can be modelled by a connector over a chromatic scale, which can be modelled by a connector over a major scale, which can be modelled by a connector over a melody, and so on.

Example 2

In a DAW production workflow

a connector over time can be modelled by a connector over a tempo grid, which can be modelled by a connector over swing and microtiming profiles, which can be modelled by a connector over groove templates for different parts (kick, hi-hats, bass, chords), which can be modelled by a connector over an arrangement structure (intro, build, drop, breakdown, outro), and so on.

Example 3

In generative graphics

a connector over colour can be modelled by a connector over an RGB (or HSL) palette, which can be modelled by a connector over palette constraints (warm/cool bias, contrast range, saturation limits), which can be modelled by a connector over a composition rule-set (background/foreground separation, accent distribution, gradient fields), and so on.

Example 4

In video editing software

a connector over time can be modelled by a connector over a timeline (frames, clips, markers), which can be modelled by a connector over edit decisions (cuts, transitions, pacing rules), which can be modelled by a connector over colour grading transforms (LUT selection, exposure/contrast curves, saturation limits), which can be modelled by a connector over an effects and export pipeline (stabilisation, compositing, audio mix, render settings), and so on.

Example 5

In a game engine

a connector over space can be modelled by a connector over a coordinate system and scene graph, which can be modelled by a connector over physics rules (collision layers, forces, constraints), which can be modelled by a connector over agent behaviours (navigation meshes, state machines, decision policies), which can be modelled by a connector over level logic (spawning, triggers, quests, difficulty curves), and so on.

Dimensions

Dimensions are the lanes inside a connector. Each dimension has its own transformation chain, and it can also connect to a child connector.

For example, one dimension can represent pitch values, another rhythmic values, and another reference values. Transformations on each dimension decide which particles are selected and how they move forward.

Dimensions make heterogeneous particles interoperable by placing them into explicit, programmable spaces.

Bindings and child connectors

PT becomes compositional when one connector can include other connectors as children. A child connector can expose open slots, and the parent can use bindings to decide which other connectors fill those slots.

A useful intuition is that bindings are the wiring layer of PT. They decide which value flows are supplied to which child positions in a larger connector graph.

This is how small reusable structures scale into larger constellations without flattening everything into one giant connector.

Transformations

Transformations are reusable rules that select, map, and shift particles on connector dimensions.

On each dimension, they are applied as an ordered chain with explicit arguments, so users can control how particle streams are selected and shifted over time.

A transformation can be simple, for example add a constant number to an input value, or it can encode much richer rules.

Transformations are written in Solidity (Ethereum's programming language for smart contracts). Many are already in the network and can be reused directly.

Conditions

Any connector can be wrapped in a condition.

If a connector's condition is not met, that connector path does not run.

A condition is Solidity code that decides whether a connector is allowed to activate.

Conditions can be:

financial, for example: the connector activates when a payment above a threshold is received, or when a token balance requirement is met.

non-financial, for example: the connector activates when an artistic or technical condition is met (time windows, permissions, external signals, governance events, or other programmable triggers).

Formats

A format describes the shape of a connector's output: which scalar streams come out and how downstream tools can interpret them.

Two connectors can behave differently internally yet still share the same format if they expose the same output structure. That is what makes reuse possible across plugins, visualisers, and other downstream tools.

In practice, formats are how decentralised.art tools recognise that one connector's outputs can stand in for another's without bespoke glue code.

Runtime controls and running instances

Besides connector structure, PT also lets users set a few runtime controls:

  • N (particle count): how many output particles to generate per output stream.
  • RunningInstances.startPoint: where index generation starts for a branch.
  • RunningInstances.transformShift: offset used to phase or shift which transformations are applied across generated steps.
  • Static vs dynamic running instances: connectors can ship with authored defaults on specific branches, and runs can also provide execution-time adjustments.

This means you can keep the same connector graph and still produce different results by changing runtime controls.

A useful intuition is that a running instance answers two questions for a branch: where does generation start, and how should the transformation chain be shifted?

Some of these defaults can be authored directly into a connector, while others can be adjusted at run time. The runner resolves them by branch position inside the connector graph.

Outputs

When a connector runs, Runner returns output particle streams. Each stream has a path in the connector graph and a list of generated values.

Those values usually correspond to things in the world outside decentralised.art: pitches, timings, colours, parameters, behaviours, or any other value space a workflow can interpret. Practically, this is often a list of index values selecting from a defined space of possibilities.

Those values become meaningful when mapped into a World or another environment: a score renderer, MIDI player, generative artwork, plugin, DAW, game engine, notation tool, or external application. PT handles the selection and transformation logic; the World or external tool renders, plays, simulates, or materialises the result.

This is how decentralised.art connects individual workflows to collective performative intelligence: participants contribute reusable operations (connectors, transformations, conditions), and others, humans and AI agents, assemble them into new executable chains.

Why does decentralised.art work this way?

Because interoperability only works when components operate on shared structures.

Instead of asking each system to produce opaque outputs, a connector selects and transforms particles from spaces that other connectors define. Each step narrows a field of possibilities into a more specific result.

This makes heterogeneous contributions compatible:

  • a human
  • an AI model
  • a rule-based process
  • a smart contract
  • a dataset

All of them can contribute connectors as long as they operate on shared value structures.

Connectors don't need to know who created the previous step. They only need to understand the format of incoming particles.

That's what makes the network scalable.

Systems that generate outputs independently are hard to combine. Systems that select and transform shared value spaces are interoperable by design.

decentralised.art is built this way because the goal is not isolated creativity. The goal is collective performative intelligence.

Vocabulary

Key terms used across decentralised.art.

World
A World is an artwork, interface, simulation, game, or application in the network that interprets compatible connector output streams. decentralised.art stores and exposes reusable procedures; each World decides how those streams become notation, MIDI, sound, visuals, behaviours, interactions, or other world-specific meaning.
Procedure
A procedure is a reusable onchain operation built from PT primitives. In practice, it is usually expressed through connectors, transformations, conditions, formats, and runtime controls.
Performative Transaction (PT)
Performative Transactions (PT) is the protocol used by decentralised.art. A PT run starts from one root connector, checks conditions, follows connector dependencies, and returns output particle streams.
Particle
A particle is a scalar value or stream element flowing through connectors during execution. Worlds and tools decide what that value addresses: pitch, time, velocity, colour, sample index, visual parameter, or another value space.
Connector
A connector is the main runnable PT object. It defines dimensions, transformations, optional child connectors, bindings, conditions, and optional default runtime settings.
Transformation
Transformations live on connector dimensions. They decide how incoming particle indexes are selected, mapped, shifted, and passed forward.
Condition
A connector only runs if its condition is met. Conditions can be financial, contextual, artistic, governance-based, or any other programmable gate.
Format
A format describes a connector's output shape. Different connectors can share a format if they emit compatible scalar streams, meaning compatible individual value streams.
Running Instance
A running instance controls where a branch of the connector graph starts generating values and how its transformation chain is shifted.
Runner
The runner executes a connector graph: it evaluates dependencies, applies each dimension's transformations, checks conditions, and emits resulting particle streams.
