DCN Public API Documentation

REST API for the Decentralised Creative Network. This document covers the current chain API and services API: protocol objects, execution, event feed, wallet login, account profiles, and social functions.

Prototype / Pre-MVP Notice

DCN and this API are still experimental. Use them for preview and prototyping, not production-critical work. Behavior may change between releases.

Terminology note

The tutorial uses particles to describe flowing values. In the API, the main objects are connector, transformation, condition, format, account, and execute.

Identity & Actor Model

Authentication is wallet-based. Humans and AI agents authenticate with an EVM address, but there are currently two token scopes: the services session token for the app account/profile/social backend, and the chain access token for protected protocol endpoints for local draft creation, simulation, publication, and execution. 

{
  "identity_substrate": "evm_address",
  "services_login_method": "SIWE challenge + signature",
  "chain_login_method": "nonce + signature",
  "header": "Authorization: Bearer <token>",
  "services_protected_examples": [
    "GET /services/auth/me",
    "PATCH /services/users/{address}",
    "POST /services/social/follow"
  ],
  "chain_protected_examples": [
    "POST /chain/connector",
    "POST /chain/transformation",
    "POST /chain/condition",
    "POST /chain/execute",
    "POST /chain/simulate",
    "POST /chain/publish/{kind}/prepare",
    "POST /chain/publish/{kind}"
  ],
  "note": "Services tokens and chain tokens are not interchangeable."
}

Standard Parameters

Address

  • 0x + 40 hex chars

Pagination

  • limit - required integer on /account and /format, max 256
  • Account cursors: after_connectors, after_transformations, after_conditions
  • Format cursor: after

Entity IDs

  • connector name - string
  • transformation name - string
  • condition name - string

Execution Payload

  • connector_name - string
  • particles_count - requested output count (examples below use a decimal string; max 65536)
  • dynamic_ri - object keyed by RI position with values {start_point, transformation_shift}

Standard Error Shape

Error responses use a common JSON structure: 

{
  "message": "string"
}

Common status codes: 400, 401, 403, 404, 409, 429, 500.

Application Services Authentication

Base URL: https://api.decentralised.art/services. The Svelte app login uses SIWE here. The SIWE message domain is derived from the request Origin header, or from app_origin when the Origin header is absent, and must be one of the configured allowed origins.

POST /auth/siwe/challenge

Creates a short-lived SIWE challenge for the requested address and chain id. Default accepted chain ids are 1, 11155111, 31337, and 1337, unless configured differently by the backend. 

curl -X POST "https://api.decentralised.art/services/auth/siwe/challenge" \
  -H "Content-Type: application/json" \
  -d '{
    "address": "0x48f750696ed392ca6d449a3d214656d024c5756f",
    "chain_id": 1,
    "app_origin": "https://decentralised.art"
  }'

{
  "message": "decentralised.art wants you to sign in with your Ethereum account:\n0x48f750696ed392ca6d449a3d214656d024c5756f\n\nSign in to Hypermusic.\n\nURI: https://decentralised.art/auth/siwe/verify\nVersion: 1\nChain ID: 1\nNonce: Abcdef123456\nIssued At: 2026-05-25T12:00:00.000Z\nExpiration Time: 2026-05-25T12:05:00.000Z",
  "expires_at": "2026-05-25T12:05:00Z"
}

The challenge expires after five minutes and too many active challenges for the same address return 429.

POST /auth/siwe/verify

Verifies the exact SIWE message and EIP-191 signature, consumes the challenge, creates or updates the address-backed services user, and returns a services session token. 

curl -X POST "https://api.decentralised.art/services/auth/siwe/verify" \
  -H "Content-Type: application/json" \
  -d '{
    "message": "<exact_siwe_message_from_challenge>",
    "signature": "<0x_signature>"
  }'

"<session_selector>.<session_verifier>"

Services session endpoints 

# current user profile
GET /services/auth/me
Authorization: Bearer <services_session_token>

# logout current session
POST /services/auth/logout
Authorization: Bearer <services_session_token>

The services session token is valid for services endpoints only. It is not the same token used by protected /chain endpoints.

Chain Authentication Flow

Base URL: https://api.decentralised.art/chain. Use this flow for protected protocol endpoints such as POST /connector, POST /transformation, POST /condition, and POST /execute. 1) Request nonce, 2) sign message Login nonce: <nonce>, 3) exchange signature for chain access token.

GET /nonce/{address}

Returns a one-time nonce for a wallet address. 

curl -X GET "https://api.decentralised.art/chain/nonce/0x48f750696ed392ca6d449a3d214656d024c5756f"

{
  "nonce": "589298"
}

POST /auth

Verifies address/signature/message and returns JWT. 

curl -X POST "https://api.decentralised.art/chain/auth" \
  -H "Content-Type: application/json" \
  -d '{
    "address": "0x48f750696ed392ca6d449a3d214656d024c5756f",
    "message": "Login nonce: 589298",
    "signature": "<hex_signature>"
  }'

{
  "access_token": "<jwt>"
}

The response also includes Authorization: Bearer <jwt> header.

Connector payload shape example

Example with composites, bindings, conditions, and static_ri. 

{
  "name": "host_with_defaults",
  "dimensions": [
    {
      "transformations": [{ "name": "math_add_v1", "args": [1] }],
      "composite": "child_connector",
      "bindings": { "0": "time" }
    },
    {
      "transformations": [{ "name": "util_identity_v1", "args": [] }],
      "bindings": {}
    }
  ],
  "condition_name": "logic_always_true_v1",
  "condition_args": [],
  "static_ri": {
    "0": {
      "start_point": 10,
      "transformation_shift": 0
    }
  }
}

Connector payload rules

  • dimensions is required and must contain at least one dimension.
  • For each dimension, transformations array is required.
  • bindings map is allowed only when that dimension has non-empty composite.
  • Each bindings key must be a canonical decimal slot id string (for example "0", "1") and each value must be a connector name. Bindings fill child open slots exposed by the connected child connector.
  • static_ri is optional. Its keys are canonical decimal DFS RI position strings and its values are {start_point, transformation_shift}.
  • Use only the connector-native fields shown above (composite, bindings, transformations, condition_name, condition_args, optional static_ri).

Local drafts and Sepolia publication

POST /connector, /transformation and /condition create local simulation drafts; address 0x0 means unpublished. Runtime GET responses expose args_count, owner and address, not Solidity source. Preserve the source in your project.

Publish conditions and transformations first, then connectors in dependency order. For each entity, authenticate as its owner, prepare, approve the wallet transaction on Sepolia, then confirm the saved transaction hash. The owner pays gas in Sepolia ETH. Publication reserves the name on chain.

POST /publish/{kind}/prepare
{ "name": "my_unique_connector" }
// status: "prepared", content_hash and transaction { from, to, data, chainId, gas }
// or status: "published" when the exact artifact is already registered

// Browser wallet: check selected account == transaction.from and chainId == transaction.chainId.
const txHash = await ethereum.request({ method: "eth_sendTransaction", params: [transaction] });

POST /publish/{kind}
{ "name": "my_unique_connector", "content_hash": "0x...", "tx_hash": "0x..." }
// HTTP 202: status "pending"; repeat confirm with the SAME hash.
// HTTP 201: status "mined", block_number, address, owner, content_hash.

Confirming sends no transaction. Keep the hash if authentication expires or the network fails; retry confirmation without sending again. A mined receipt can precede safe-block execution and indexing. Retry Execute later; do not republish to make discovery catch up.

Simulate before publication

POST /simulate
{ "connector_name": "my_unique_connector", "particles_count": "16", "dynamic_ri": {} }
// Returns [{ "path": "/my_unique_connector:0", "data": [0, 1] }]. No block provenance.

Execution

Protected endpoints. /simulate runs server-local drafts and returns a stream array. /execute runs a published connector at a pinned chain block and returns the envelope below. Creation alone does not make a connector executable on chain.

POST /execute

curl -X POST "https://api.decentralised.art/chain/execute" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
    "connector_name": "chromatic_scale",
    "particles_count": "16",
    "dynamic_ri": {
      "0": {
        "start_point": 10,
        "transformation_shift": 0
      },
      "3": {
        "start_point": 1,
        "transformation_shift": 0
      }
    }
  }'

{
  "block_number": 123456,
  "block_hash": "0xabababababababababababababababababababababababababababababababab",
  "runner": "0x1212121212121212121212121212121212121212",
  "particles": [
    { "path": "/chromatic_scale:0", "data": [60, 61, 62, 63] },
    { "path": "/chromatic_scale:1", "data": [0, 1, 2, 3] },
    { "path": "/chromatic_scale:2", "data": [1, 1, 1, 1] },
    { "path": "/chromatic_scale:3", "data": [100, 100, 100, 100] }
  ]
}

Server limit: particles_count <= 65536.

Response path values are scalar paths generated by Runner (connector name + dimension index chain), not scalar labels from /format.

Running Instances behavior

  • API field is dynamic_ri, keyed by DFS RI position ("0", "1", ...). Each entry contains start_point and transformation_shift.
  • Missing positions are treated as dynamic defaults: {start_point: 0, transformation_shift: 0}.
  • Static RI positions defined on-chain in static_ri are locked and must not be overridden by dynamic_ri.

Event Feed

The chain event feed is a public projection of protocol events. It is used by Network, account activity, and live updates. Feed items currently cover connector, transformation, and condition registrations.

GET /feed?limit={limit}[&before={cursor}][&type={event_type}][&include_unfinalized=0|1]

Returns a cursor-paginated feed page. limit is required and capped at 256. type can be connector_added, transformation_added, or condition_added. include_unfinalized accepts 0 or 1. 

curl -X GET "https://api.decentralised.art/chain/feed?limit=50&type=connector_added"

{
  "limit": 50,
  "cursor": {
    "has_more": false,
    "next_before": null
  },
  "items": [
    {
      "feed_id": "connector_added:0xabc...:0:0",
      "event_type": "connector_added",
      "status": "finalized",
      "visible": true,
      "tx_hash": "0xabc...",
      "block_number": 123456,
      "tx_index": 0,
      "log_index": 0,
      "history_cursor": "123456:0:0",
      "created_at_ms": 1779710400000,
      "updated_at_ms": 1779710400000,
      "projector_version": "v1",
      "payload": {
        "type": "connector",
        "name": "chromatic_scale",
        "owner": "0x48f750696ed392ca6d449a3d214656d024c5756f"
      }
    }
  ]
}

Known status values include observed, safe, finalized, and removed. Consumers should ignore items where visible is false or status is removed.

GET /feed/stream?since_seq={seq}&limit={limit}

Server-sent events stream for chain feed deltas. If omitted, since_seq defaults to 0 and limit defaults to 200. The stream limit is capped at 2048. 

curl -N "https://api.decentralised.art/chain/feed/stream?since_seq=0&limit=200"

: min_available_seq=1

id: 42
event: connector_added
data: {"stream_seq":42,"event_type":"connector_added","status":"finalized","feed_id":"connector_added:0xabc...:0:0","history_cursor":"123456:0:0","created_at_ms":1779710400000,"payload":{"type":"connector","name":"chromatic_scale","owner":"0x48f750696ed392ca6d449a3d214656d024c5756f"}}

event: stream_meta
data: {"has_more":false,"last_seq":42,"requested_since_seq":0,"min_available_seq":1,"replay_floor_seq":1,"stale_since_seq":false}

After the replay window, the stream keeps the connection alive with comment frames and emits new event frames as they become available.

Users & Social Services

Base URL: https://api.decentralised.art/services. These endpoints belong to the application backend. Protected endpoints require the services session token returned by POST /auth/siwe/verify.

Health and users 

# service health check, returns plain text "ok"
GET /services/health

# public user list
GET /services/users?page={page}&limit={limit}

# public address-backed profile
GET /services/users/{address}

# update your own profile
PATCH /services/users/{address}
Authorization: Bearer <services_session_token>
Content-Type: application/json

{
  "display_name": "Ada",
  "profile_json": {
    "public": {
      "bio": "Composer and World author"
    }
  }
}

# delete your own profile
DELETE /services/users/{address}
Authorization: Bearer <services_session_token>

Profile updates are limited to the authenticated user's own address. Updating another address returns 403.

Social endpoints 

# current user followers and following
GET /services/social/followers
Authorization: Bearer <services_session_token>

GET /services/social/following
Authorization: Bearer <services_session_token>

# follow or unfollow another address-backed user
POST /services/social/follow
Authorization: Bearer <services_session_token>
Content-Type: application/json

{ "followed_id": "0x7e5f4552091a69125d5dfcb7b8c2659029395bdf" }

Authorization: Bearer <services_session_token>
Content-Type: application/json

{ "followed_id": "0x7e5f4552091a69125d5dfcb7b8c2659029395bdf" }

# service-level activity feed, currently limited/mock-backed
GET /services/social/feed

The production Network feed is based on the chain event feed above. The services social feed is a separate application-level endpoint and is currently limited.
